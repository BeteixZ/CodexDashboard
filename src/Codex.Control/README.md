# Owned App Server control

This `net10.0` library has no UI dependency. It references the canonical host and task identities in `Codex.ReadOnly`. It does not reference `Assistant.Core`, read credentials, open a production Codex home, or start a process during construction.

Implemented wire paths:

- `initialize` / `initialized`, pinned to the locally generated stable **0.147.0** schema. The response's version, platform and exact configured Codex home must match. The response has no capability list; the library does not invent one.
- Owned `thread/start`, `turn/start`, `turn/steer` with `expectedTurnId`, `turn/interrupt`, `thread/name/set`, `thread/archive`, `thread/unarchive`.
- `turn/started`, `turn/completed`, approval-related `thread/status/changed`, command/file approval requests, and `serverRequest/resolved`.
- Read-only reconciliation using `thread/read`; exact-turn final messages, command items and file-change items remain recorded evidence, never independent verification.
- Newline JSON-RPC over injected streams or a process owned by this transport. Local processes use `ArgumentList` and an explicit Codex home. SSH uses a validated configured alias, strict host-key checks, no interactive authentication and separately POSIX-quoted remote values. Only the process created by this instance, including its own descendants, can be stopped.

`OwnedServerConfiguration` is trusted host configuration. Do not expose its construction, process launch arguments, runtime-verification objects or ownership handles as model tools. A tool may supply an already authorized operation ID and refer to a handle resolved by the host. `CreateOwnedTask` must select an exactly configured project directory and model, and explicitly choose `untrusted`/`on-request` plus `read-only`/`workspace-write`. Dangerous permission modes and automatic reviewer delegation are not supported. A returned thread with a different directory/model/permission policy, additional writable roots or network permission is not adopted.

Every control capability is disabled without a `RuntimeVerification` record matching the endpoint/profile, backend, exact version, platform, project/model configuration digest, expiry and method scope. Synthetic replay evidence can enable only an explicitly synthetic connection. **This repository ships no runtime acceptance evidence and does not enable real owned control by default.** These records are configuration evidence, not cryptographic authentication; only trusted host code may install them.

Ownership is deliberately narrow: a validated `thread/start` reply must be durably recorded before this client exposes an `OwnedTaskHandle`. Another client cannot use that handle. A notification or a model's owner declaration never creates ownership. Same-instance reconnection retains handles but permanently becomes read-only. It initializes the new connection and waits for explicit `ReconcileAsync`; it never resumes or starts a turn, never replays an uncertain write, and never silently creates a replacement task.

Creation now requires an injected `OwnedProvenanceStore`. The host supplies an `IOwnedProvenanceStorage` and an authenticated `IOwnedProvenanceProtector`; there is no plaintext protector or fallback. The host owns encryption keys, storage permissions, path selection and the store's lifetime. Keep all these APIs outside model tools and dispose the store only after in-flight client operations have finished. One store instance can attach to one client. `FileOwnedProvenanceStorage` is an optional bounded encrypted-frame store, with exclusive writer access, immutable sequence numbers, frame hashes and commit markers, and `Flush(true)` before acknowledgement. Damaged, incomplete or already-existing empty data is preserved and blocks further use; there is no automatic truncation or recovery. Only an atomically created file may initially be empty. Authenticated JSON also rejects duplicate or unknown fields. Its local filesystem durability still requires platform acceptance before production enablement.

The protected creation proof binds exact canonical endpoint/profile, backend, synthetic/runtime domain, project/model/home configuration digest, thread, project directory, model, conservative permission policy, original create operation ID, server version, creation time, connection epoch and a digest of safe validated response fields. It contains no prompt, preview, auth data, turn history or arbitrary error text. Sequence and configuration are also bound as protector purpose. The protector must authenticate both ciphertext and purpose. Storage/protector implementations are trusted host dependencies, not a sandbox against malicious host code with the key.

`RestoreReadOnlyAsync()` accepts no ownership records from the caller. It reads and validates the entire injected store after exact server initialization, then returns `OwnedTaskHandle.Access == RestoredReadOnly` and the immutable original `Creation` evidence. Restored task state starts at `Unknown`; current facts require explicit `ReconcileAsync` / `ReadReportAsync`. Restoration alone blocks mutations and actionable approvals. With method-specific runtime acceptance, the host may explicitly call `ResumeAsync` after reconciling an idle or terminal task and checking its durable operation ledger. The exact thread, directory, model and permissions must match the persisted creation evidence. Successful resume promotes only that handle to `ResumedThisSession`; it does not start a turn or replay work. New work requires separate current authorization. A fresh explicitly authorized create operation may append a new task to a writable verified store after restart; historical create operation IDs remain rejected and old handles retain their access state. Same-instance transport reconnection remains read-only. Exact read-only restoration is allowed without runtime write acceptance; this does not enable runtime control.

Creation/persistence uncertainty remains visible. If the server may have created a thread but protection, append, cancellation or connection validation fails, the call returns `Unknown` with its original operation ID and no handle. The caller must retain its pre-dispatch durable operation and reconcile manually; this result never means it is safe to retry. If a complete protected proof survived a lost storage acknowledgement, a later process may recover that proof **read-only**, but the unknown outer operation is not silently marked successful. A lost backend reply produces no proof and cannot be adopted. This creation-proof store is not a business ledger and does not cover unknown dispatch intent, cross-process retry deduplication, complete-file deletion or rollback detection. Restoring a previous complete proof prefix can only remove available handles; it cannot grant additional control. Hosts needing rollback detection must supply separately protected monotonic storage and retain the operation ledger.

The caller owns the durable business ledger and current-user authorization. Pass its operation ID into each control call. Consume `ReadObservationsAsync` to associate lifecycle observations with that ID. Observations carry safe codes, identities and state, not input text or arbitrary server errors. `Reconciliation` is explicit for exact-turn read evidence and exact consumed-request resolution; ordinary direct replies do not carry it. A late ordinary lifecycle event may update the task's observed state while its uncertain operation stays `Unknown`; explicit exact-turn read reconciliation is required to advance that operation. A known terminal operation is never downgraded by a later malformed or failed direct reply. The bounded in-memory wire correlation cache rejects operation-ID reuse; it does not provide cross-process deduplication or backend exactly-once guarantees. The outer ledger must persist dispatch intent before calling and preserve unknown operations across restart. A turn ID learned after creation/start is separately reported; the host must preserve the original authorization target and record evidence for this additional binding instead of silently replacing it.

Response acceptance, a running turn and completion are distinct. A `turn/start` response reporting `inProgress` still produces `Accepted` until a matching lifecycle event arrives. Interrupt acknowledgement does not establish interruption. Steer acceptance does not prove that its instruction affected the result. Approval response writes have no RPC acknowledgement: they stay `Unknown` until the matching server request is resolved. Every approval binds its typed request ID, connection epoch, host/profile, thread, turn, project, item, expiry and focus revision. Reservation occurs before writing and is never reset after uncertainty. Resolved, expired, old-focus and old-connection requests cannot be reused. File approvals require the same item's observed file-change details before acceptance is available; missing details or `grantRoot` expansion permit only declining or cancelling. Operation details and summaries are untrusted display evidence, never executable instructions.

The host calls `SetFocus` before presenting approvals for its current task. A focus change invalidates pending approval contexts. Presenting previously invalidated approvals again, multi-task approval selection and restoring write access after transport reconnect require explicit host-ledger integration and current method-specific verification; there is no unsafe import or generic override API. Unknown task state prevents starting another turn on that handle.

The Windows host provides WeChat/tool wiring, current-user protected provenance storage, and explicit same-task restart recovery in src/Assistant.Windows. These integrations do not enable every method or backend by default. Desktop coexistence, remote SSH environments, approval round trips and transport-failure boundaries still need scenario-specific acceptance. Live turn-diff streaming and generic capability discovery beyond the pinned schema and installed acceptance scope are not provided by this library. Synthetic library tests alone do not establish end-user control acceptance.

Tests:

```powershell
dotnet build tests/Codex.Control.Tests/Codex.Control.Tests.csproj -m:1
dotnet run --no-build --project tests/Codex.Control.Tests/Codex.Control.Tests.csproj -- artifacts/control-tests
```

To include schema-conformance checks, pass a separately generated schema directory as the second positional argument. The console test executable acts as its own fake child process. It tests real pipes, concurrent request IDs, server requests/responses, cancellation after write, abrupt EOF, bounded framing, process cleanup and launch argument quoting. Provenance tests inject failures at write/commit/flush boundaries, tamper with ciphertext and authenticated fields, alter endpoint/profile/configuration, and kill a real synthetic writer process before launching a separate read-only recovery process. The public AES-GCM fixture key exists only in the test project and must never protect production data. All task actions use synthetic objects and no real Codex process or credential store.
